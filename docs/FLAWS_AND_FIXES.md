# Flaws found in the two predecessor projects — and what the merge does about them

Two projects were merged:

* **A** = `/mnt/c/Users/DELL/threat detection project` (real-WESAD ML core, firmware, tests)
* **B** = `/mnt/c/Users/DELL/Documents/esa project` (FastAPI + dashboard + vision + fusion)

Severity legend: **P0** correctness / data integrity (would fail a review if probed) ·
**P1** architecture / robustness · **P2** ML quality · **P3** hygiene.

Each item: *evidence → impact → fix*.

---

## P0 — Correctness & data integrity

### F1. Project B's "WESAD" is synthetic, but documented as real
* **Evidence:** `B/data/wesad/{S2,S3,S4}/*.pkl` are all exactly `27 938 584` bytes —
  generated by `B/scripts/generate_synthetic_wesad.py`. `B/README.md` claims real WESAD.
* **Impact:** every number B reports is unverifiable, and the claim is false. This is
  the single most dangerous flaw — it is a *data-integrity* problem, not a bug.
* **Fix:** the merged project loads **real WESAD** from `data/wesad/S*/S*.pkl`
  (15 subjects, per-file sizes 827 MB – 1.13 GB, verified to differ). The synthetic
  generator is deleted. Every reported metric in the merged repo comes from real data.

### F2. Project B leaks subjects across train/val
* **Evidence:** `B/backend/ml/train.py` → `random_split(dataset, [train_size, val_size])`
  applied to windows concatenated from **all** subjects.
* **Impact:** windows from the same person appear in train and validation, inflating
  every reported score. This is the single most common WESAD evaluation error.
* **Fix:** subject-independent split enforced structurally —
  train `S2–S11`, val `S13–S14`, test `S15–S17`. Subjects are partitioned *before*
  windowing, so a window can never straddle a split. See `threatwatch/data/dataset.py`.

### F3. Project B fits the standardizer on all data (normalization leakage)
* **Evidence:** `B/scripts/preprocess_wesad.py` → `preprocessor.fit(all_raw_signals)`
  runs before any split exists.
* **Impact:** val/test statistics leak into the scaler used for training.
* **Fix:** `Standardizer.fit()` is called on **train windows only**; the fitted
  mean/std are applied to val/test and persisted next to the checkpoint together with
  their channel list, so live inference cannot silently mismatch.

### F4. Project B's model consumes signals the hardware cannot produce
* **Evidence:** `B/backend/data/wesad_adapter.py` reads
  `raw_data["signal"]["chest"]` → `ECG, EDA, Resp, Temp, ACC`. The BOM is
  MAX30102 (PPG → HR) + MPU6050 (accelerometer/gyro) — a **wrist** device with no ECG.
* **Impact:** the learned distribution is not reproducible by the physical prototype;
  the "live hardware" path is therefore disconnected from the trained model.
* **Fix:** train on WESAD **wrist** channels — BVP→HR, EDA, TEMP, ACC — resampled to
  32 Hz. Two channel sets are produced: `full` (with EDA) and `hw` (hardware-only,
  no GSR sensor) so the accuracy cost of the missing sensor is measured, not hidden.

### F5. Missing WESAD wrist accelerometer unit conversion (×64 error)
* **Evidence:** WESAD's wrist device is an Empatica E4 whose accelerometer is reported
  in units of **1/64 g**. `A/fittrack/data/wesad.py` documents `ACC_LSB = 64.0`;
  B never applies it.
* **Impact:** the acceleration channel is off by ×64, i.e. effectively dead as a feature.
* **Fix:** `/64` conversion applied in the wrist loader so units match the MPU6050
  (±2 g full scale).

### F6. Project B's resampling arithmetic does not produce the rate it claims
* **Evidence:** `B/backend/data/wesad_adapter.py`:
  `downsample_factor = raw_hz // target_hz` → `700 // 32 = 21`; and `700 / 21 = 33.33 Hz`,
  not 32 Hz. `target_len = orig_len // 21` compounds the mismatch.
* **Impact:** every window length, window count and "Hz" label is subtly wrong, and the
  window that the live replay produces does not match the window the model was trained on.
* **Fix:** resample **by timestamp** onto an explicit 32 Hz grid
  (`np.interp` over `t = n / fs_native`), independent of each channel's native rate.
  One code path is used for training data and for live replay.

### F7. Project B's firmware fabricates SpO₂
* **Evidence:** `B/firmware/arduino_wearable/arduino_wearable.ino`:
  `ratio = red/ir; spo2Calc = 110.0 - 15.0*ratio;` then smoothed into `estimatedSpO2`.
* **Impact:** a made-up physiological number is displayed as a measurement.
* **Fix:** SpO₂ is emitted as an **empty field** (uncalibrated), matching the honest
  protocol from A. A comment states exactly what calibration would be required.

### F8. Project B's ESP32 adapter invents sensor values
* **Evidence:** `B/backend/data/esp32_adapter.py` defaults
  `eda=3.0`, `respiration=16.0`, `heart_rate=75.0`, `temperature=34.0` when a field is
  absent, and its `connect()` is a stub that always returns `False`.
* **Impact:** absent sensors silently become plausible fake readings that reach the model.
* **Fix:** the unified packet schema uses `None` for "not measured" and the window
  builder interpolates only across genuinely valid samples. A real ESP32 source
  (serial + BLE NUS, same CSV protocol) replaces the stub.

### F9. Project B's replay window wraps around, feeding a discontinuous window to the model
* **Evidence:** `B/backend/data/replay_engine.py::get_current_window()` — when
  `idx < WINDOW_SAMPLES` it concatenates the **tail** of the recording with the head.
* **Impact:** at every startup/loop the model receives a window containing a
  time-discontinuity (end followed by beginning), producing nonsense inference.
* **Fix:** return `None` until a full contiguous window exists; the caller displays a
  "buffering" state. Verified by test.

## P1 — Architecture & robustness

### F10. Vision inference blocks the asyncio event loop
* **Evidence:** `B/backend/main.py::run_pipeline_loop()` calls
  `self.pose_detector.detect(raw_frame)` (YOLOv8) inline in the async loop that is also
  responsible for WebSocket broadcast at 20 FPS.
* **Impact:** a slow YOLO frame stalls telemetry for all clients — the dashboard stutters
  exactly when the scene is interesting.
* **Fix:** a dedicated `VisionWorker` thread runs capture → detect → analyse → overlay and
  publishes an immutable latest snapshot. The event loop only reads the snapshot.
  Vision runs at its own rate and can never throttle telemetry.

### F11. There is no dispatch — "emergency dispatch" is a log line
* **Evidence:** `B/backend/fusion/state_machine.py` sets `emergency_dispatched = True`
  and returns the string *"simulated emergency payload dispatched"*; nothing is sent.
* **Impact:** the system's headline capability ("alert on threat") does not exist.
* **Fix:** a `threatwatch/alerts` package with a pluggable `Notifier` interface,
  a **Telegram** backend (implemented), and a dispatch manager providing
  cooldown, de-duplication, retry with backoff, and an audit trail. Notification
  failure can never crash the pipeline.

### F12. Alert state machine timer/hysteresis bugs
* `_threat_timer_start` is never cleared when THREAT is entered → re-entry timing is wrong.
* `_recovery_timer_start` is not cleared when leaving ALERT ACTIVE.
* SAFE → CAUTION is skipped on the first over-threshold sample (the `if/elif` chain
  only reaches the `else` on the *second* sample).
* No alert cooldown → an oscillating score can re-notify on every cycle.
* **Fix:** rewritten FSM: explicit per-transition timer reset, monotonic clock,
  documented transition table, alert cooldown, and unit tests for every transition.

### F13. Fusion engine has dead parameters and inline magic numbers
* **Evidence:** `B/backend/fusion/fusion_engine.py::fuse(demo_override, demo_threat_level)`
  — `demo_override` is always `False` at the only call site; thresholds `0.65/0.60/0.50/0.46`
  are inline literals duplicated from `config.py`.
* **Fix:** dead parameters removed; all thresholds named in `config.py`; the suppression
  rules are documented and unit-tested (high-sensor/calm-vision is capped at CAUTION, etc.).

### F14. Configuration duplicated across two projects
* **Evidence:** two window sizes (`WINDOW_SAMPLES=128` in B vs `960` in A), two label maps,
  two sampling-rate constants, two `feature channel` lists.
* **Impact:** A model trained with one window length cannot be loaded by the other project.
* **Fix:** exactly one `threatwatch/config.py`. The window length used at training time is
  written into the checkpoint and the live window is derived from it, so a mismatch is
  impossible.

### F15. No tests in project B; project A's tests bound to the old package name
* **Fix:** one merged suite covering the WESAD loader, windowing/scaler, serial CSV
  round-trip, replay engine, fusion rules, the state machine, and the alert manager.

## P2 — Machine-learning quality

### F16. Deep models are badly under/over-fit
* **Evidence:** `A/results/cnn_metrics.json` → `"best_epoch": 1` (peaks immediately, then
  overfits); `A/results/bilstm_metrics.json` → val_loss rises `1.61 → 4.34` while train
  loss falls to `0.007`.
* **Diagnosis:** 30 s @ 32 Hz = **960 timesteps** is very long for a BiLSTM; LR 1e-3 with
  no warmup; class imbalance; only 2156 training windows.
* **Fix:** configurable window (default **15 s** = 480 samples), LR warmup + cosine decay,
  gradient clipping, label smoothing, stronger recurrent dropout, and a stride-4
  convolutional tokenizer in front of attention (cuts O(T²) attention cost ~16×).

### F17. The `amusement` class collapses and drags macro-F1 down
* **Evidence:** per-class F1 for amusement: RF 0.29, logistic 0.34, CNN+Transformer 0.22.
* **Fix:** report **both** tasks — 3-class and **binary (stress vs baseline)**. Binary is
  the literature-standard target and materially higher; the write-up explains that
  amusement is the hardest class on wrist-only signals and why.

### F18. The pure Transformer never converged and was reported as a limitation
* **Fix:** with the shorter window + warmup + correct batch size it is trainable; the
  new measurement is reported either way, honestly.

### F19. Emotion-free hard-coded temperature scaling (T = 2.2)
* **Evidence:** `B/backend/ml/inference.py` → `scaled_logits = logits / 2.2`.
* **Fix:** temperature fitted on the **validation set** (minimise NLL), persisted in the
  checkpoint. Reported as a calibration metric (ECE before/after).

### F20. No edge-export path, although the brief asks for quantisation/deployment
* **Fix:** `scripts/export_onnx.py` produces an ONNX graph that can be inspected in Netron,
  plus a documented PyTorch → ONNX → TFLite route and a latency/size measurement.
