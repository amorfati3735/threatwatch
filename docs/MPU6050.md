# MPU6050 (GY-521) — hardware notes for the ThreatWatch wearable

> **TL;DR — read this before touching the IMU code.**
> The module on this rig is sold as "MPU6050" but the chip reports
> **`WHO_AM_I = 0x70`, i.e. it is a MPU6500** (very common on GY-521 clones).
> It is **fully compatible** with this project's firmware (which never checks the
> ID), but it **breaks the Adafruit_MPU6050 library** (which does), and it makes
> the `temp` channel read **≈ +11.5 °C too high** with the MPU6050 formula the
> firmware uses. Everything else — registers, scales, addresses — is identical.

## 1. How this was established (2026-10-13)

Raw probe on the actual rig (`firmware`-level register read, see §5):

```
--- bus scan (ACK list) ---
ACK 0x3C   (SSD1306 OLED)
ACK 0x57   (MAX30102)
ACK 0x68   (IMU — present and answering)
WHO_AM_I raw = 0x70 (expect 0x68), endTx=0
mpu.begin() #1 = false      ← Adafruit lib rejects the ID
mpu.begin() #2 = false
```

The bus and wiring were correct the whole time; only the library's identity
check refused the chip.

### WHO_AM_I values (register `0x75`, bits 6:0)

| Value | Chip |
|---|---|
| `0x68` / `0x69` | MPU6050 (AD0 low / high) |
| **`0x70`** | **MPU6500 ← this rig** |
| `0x71` / `0x73` | MPU9250 / MPU9255 |
| `0x12` | ICM-20602 (different family, not register-compatible with the code below) |

Check yours any time with a 4-line sketch: address `0x68`, write `0x75`,
repeated-start read 1 byte.

## 2. Wiring (8-pin GY-521)

| GY-521 pin | Connect to | Note |
|---|---|---|
| VCC | 3V3 | module has its own regulator path; 3.3 V keeps logic at 3.3 V |
| GND | GND | common ground with ESP32 |
| SCL | GPIO22 | shared I²C bus |
| SDA | GPIO21 | shared I²C bus |
| XDA, XCL | **leave unconnected** | auxiliary I²C master for external mags |
| AD0 | **leave unconnected** | address select → bus scan confirms **0x68** floating |
| INT | optional → GPIO26 | not used by current firmware (polled sampling) |

ESP32 GPIOs are **not 5 V tolerant** — never power this bus from 5 V.

## 3. Library compatibility

| Approach | Works with 0x70? | Where |
|---|---|---|
| **Raw registers (this project's firmware)** | ✅ | `firmware/esp32_wearable/esp32_wearable.ino` — `mpuInit()` only checks that the address **ACKs**, never reads WHO_AM_I |
| `all_sensors_test` smoke sketch (host of this discovery) | ✅ | raw registers, accepts 0x68/0x69/0x70/0x71/0x73 |
| **Adafruit_MPU6050** | ❌ | `Adafruit_MPU6050.cpp` `begin()`: `if (chip_id.read() != MPU6050_DEVICE_ID) return false;` — hard-coded `0x68`, no override |
| Rowberg I2Cdev `MPU6050::testConnection()` | ❌ | compares against 0x68/0x69 |

Rule for contributors: **if a bus scan sees 0x68 but a library says "not
found", read WHO_AM_I before re-checking your wiring.**

## 4. What the firmware uses (identical on 6050 and 6500)

| Register | Address | Value written | Meaning |
|---|---|---|---|
| PWR_MGMT_1 | `0x6B` | `0x00` | wake, internal 8 MHz osc |
| ACCEL_CONFIG | `0x1C` | `0x00` | ±2 g → scale **16384 LSB/g** |
| GYRO_CONFIG | `0x1B` | `0x00` | ±250 °/s → scale **131 LSB/(°/s)** |
| CONFIG (DLPF) | `0x1A` | `0x03` | ≈44 Hz low-pass |
| data burst | `0x3B…0x48` | — | ax,ay,az,temp,gx,gy,gz as int16 big-endian |

These settings match the write-up (§6.3: “±2 g and ±250 °/s with a ~44 Hz
digital low-pass”). The MPU6050 and MPU6500 register maps are identical for
every register above, which is why the firmware runs unmodified.

## 5. The temperature offset quirk (affects the `temp` feature channel)

- MPU**6050** datasheet formula: `°C = raw / 340 + 36.53`
- MPU**6500** datasheet formula: `°C = raw / 340 + 25`
- Firmware (`mpuRead()` line ~118) uses the **6050** formula unconditionally.

Measured on this rig, same instant, same chip:

| Sketch | Formula base | Reported |
|---|---|---|
| ThreatWatch firmware stream | 36.53 | **40.77 °C** |
| `all_sensors_test` (0x70-aware) | 25.0 | **29.2 °C** ← believable die temp |

→ constant **+11.53 °C bias** whenever this board is the hardware.

Impact and mitigations:
- `temp` ∈ `HW_FEATURE_CHANNELS`, so the model does see it. The winning model
  uses **per-window z-normalisation**, which cancels a constant offset by
  construction → predictions unaffected. The *global* standardiser variant
  would carry the bias.
- Absolute die temp shown/logged anywhere will be wrong by +11.5 °C.

Optional one-line fix in `mpuInit()` (keeps 6050 behaviour for real 6050s):

```cpp
uint8_t id = 0;
Wire.beginTransmission(MPU_ADDR); Wire.write(0x75); Wire.endTransmission(false);
Wire.requestFrom((uint8_t)MPU_ADDR, (uint8_t)1); id = Wire.read();
const float TEMP_BASE = (id == 0x70 || id == 0x71 || id == 0x73) ? 25.0f : 36.53f;
// then: tempC = raw[3] / 340.0f + TEMP_BASE;
```

## 6. Verified behaviour on this rig (2026-10-13)

- Bus scan: `0x3C + 0x57 + 0x68` — all three modules, one 4-wire bus, no jams.
- Acceleration sanity: `√(ax²+ay²+az²) ≈ 1.00 g` at rest (correct scaling).
- Firmware CSV stream over COM11 at ~12.4 Hz measured (nominal loop is 20 Hz —
  the gap is loop overhead, worth noting if you assume exactly 50 ms spacing;
  the pipeline resamples to 32 Hz by timestamp, so it does not matter downstream).
- End-to-end: stream → bridge → `scripts/live.py` → CNN predicts
  `win=(480, 7)` windows and prints `STATE = BASELINE …`. Bridge scripts:
  wired — `scripts/windows_serial_bridge.py`; **Bluetooth LE (board on a power
  bank, no USB)** — `scripts/windows_ble_bridge.py` (bleak, NUS "ThreatWatch",
  verified 2026-10-13: full CSV lines over BLE, MTU 23 caused no truncation);
  both feed `scripts/ws_pty_relay.py` → pty → pipeline.
